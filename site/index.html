Open firmware for digital storage oscilloscopes

One family: the same features, web UI and look on every instrument. The demos below run the firmware's core in a browser tab, against a simulated board with a signal generator on its inputs. They show the product; the full simulator is what tests it.

Two kinds of simulation

The browser demo shows the product. The full simulator tests the firmware.

Both run without a scope on the desk, but they answer different questions. If you are deciding whether a scope works, it is the second one that counts.

Browser demo

WebAssembly, in a browser tab

for trying the look and feel

The core (engine, menus, renderer, web UI, decoders and measurements) is compiled to WebAssembly and runs against a simulated board built from the scope's profile and its panel's key table. A signal generator feeds its inputs.

It shows what using the firmware is like. It does not run the scope's own board code, its FPGA or its operating system, and its timing and frame rates are the browser's, not the scope's. We compare it with a real SDS1000CML+ by running the same recorded sessions on both and replaying records captured on the unit.

Full simulator

The real firmware under QEMU

for end-to-end testing

The scope's actual ARM firmware binary runs under QEMU with its Linux, against a model of the scope's hardware: registers, FPGA, DMA and interrupts, the analog front end, the panel and the touchscreen. The open FPGA design can be simulated in the loop with Verilator.

This is where installing, updating, power cuts, injected faults, trigger firing, protocol decoding and the web UI are tested end to end. The SDS800X HD is verified this way, since no unit has been on a bench yet. Its hardware model is kept in a private reference workspace for now; the test harness and its results are in the public repository.

Features

What the firmware does

These are captures from an SDS1102CML+ running the released firmware. The features live in the shared core, so a new scope gets them through its board package.

52 serial protocols

Each with a hardware trigger, a decoder and AUTO detection. A bus can also be decoded as a gap-free stream, or drawn as what it carries, like MIDI on a piano.

Eye diagram and jitter

The eye of a 104 Mbit/s data line, with eye height and width and TIE jitter.

Spectrum and spectrogram

An FFT with a peak table, and the spectrogram: the spectrum over time.

Bode plots

Gain and phase against frequency, from a stepped source on C1 and the circuit's output on C2.

SOUND

Level meters, a tuner, envelope and modulation for an audio signal streamed without gaps. The web UI can play it back.

Mask testing

Stack a master from many captures, then test live captures against its mask and count the failures.

  • 18 automatic measurements with statistics, cursors and math
  • A web UI with the same workspaces as the scope, and a phone remote
  • SCPI over VXI-11 on the network
  • Two install slots with A/B updates; on the SDS1000CML+ nothing is flashed, and a power cycle brings back the factory firmware
  • On the SDS1000CML+: 500 MS/s on both channels into 1 M-sample records, super-resolution, and a gap-free stream buffered in the scope's SRAM

How it's built

The core is the product. A scope is a board package.

open-dso-core holds everything that doesn't depend on one instrument: the acquisition engine, instrument state, decoders, measurements and analysis, the display renderer, the web server and client, SCPI, the update supervisor, the design system and the test tools.

A scope repository implements the hardware abstraction layer for its board, and holds its specifications, its profile, its FPGA images and its installer. A feature written once in the core reaches every scope. A difference between scopes is data in the scope's profile, not a branch in core code.

Specifications

Bring your scope

Port open-dso to your oscilloscope

The firmware is a Linux application written in Go, so your scope needs a processor that runs Linux. You write the board layer: the code that talks to your hardware, a profile that describes it, and specifications in your own words. The core gives you the rest of the product.

You write one repository

  • Specifications of the hardware and its interfaces
  • hal.Board platform, planner, acquirer, readout, trigger, front end, display, input, storage
  • profile.yaml channels, code format, rates, display, inputs, and why any optional part is absent
  • FPGA images if the board has an FPGA you load
  • Installer and recovery and a tested way back to the vendor firmware

The core gives you open-dso-core

  • Acquisition engine and instrument state
  • 52 protocol decoders with AUTO detection
  • Measurements and analysis FFT, spectrogram, Bode, eye and jitter, masks, SOUND
  • Display renderer and UI model for a front panel or a touch screen
  • Web UI, phone remote, SCPI the same API on every scope
  • Update supervisor A/B slots
  • Design system and test tools listed below

The path

  1. Specifications

    Describe the hardware and its interfaces in your own words. Hardware facts stay marked UNVERIFIED until they are measured on a unit.

  2. A simulator before a unit

    Build a model of the board that the app can run against. Everything after this is developed and tested there first.

  3. The board, one interface at a time

    Implement hal.Board against the simulator, write profile.yaml, and run the core's conformance suite.

  4. The product comes with it

    Your main builds the board and runs the core. What the board can't do, it reports as absent with a reason, and the UI refuses it with that reason.

  5. First contact, staged

    A read-only census of the unit, then reading while the vendor firmware still owns the front end, then writes, then the display. A recovery procedure is proven first.

  6. First release

    When the firmware runs on a unit, installs and recovers safely, and passes the family's regression checklist. Until then it is marked verified in simulation only. The repository itself can be public at any stage, once its tree and history pass a provenance review.

The full guide: adding a scope

It has been done once without a unit

The SDS800X HD was ported entirely in simulation. Its board layer implements the whole HAL, runs the core's conformance suite inside its simulator, and passes its parity harness for every trigger type, readout, the front end and self-calibration. It has not run on a real unit yet.

  • ~15,000lines of Go in the SDS800X HD's own app, its whole board layer
  • ~89,000lines of Go in the core, plus about 32,000 lines of JavaScript for the web client
  • 2 filesmake its browser demo: a 100-line profile and a 116-line demo file with the panel and key table, on the core's simulated board

The tools you get

HAL conformance suite
hal/conformance: the HAL contract as 23 Go subtests. Run it against your board, its fakes or your simulator. A clause your harness can't exercise is skipped with its reason, never passed.
Simulated board and browser demo
hal/simboard plus your profile and a demo file gives you a running scope in a browser tab before you have written any hardware code.
Recorded sessions
session and cmd/dsosessions: one file of operator actions and input signals, replayed on the real scope, the demo or your simulator, with the states compared field by field.
Design system
design/: the palette, channel colours, layout and the 5×7 LCD font, so your scope looks like the others.
Provenance rules
What may go in a public repository, and what may not.

Provenance in one line: write from your own specifications. Hardware facts are fine, in your own words; vendor code, files, strings and symbol names never go into a public repository.
